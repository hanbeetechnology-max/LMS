# HanbeeLms — Complete LMS for Staff & Students

## Context

`HanbeeLms` is currently an empty project directory — this is a from-scratch build. The goal is a complete Learning Management System serving two user types, Staff (instructors/admins) and Students, covering the full loop of course delivery, enrollment/rosters, and attendance/scheduling/communication. The user confirmed the stack (React+Vite frontend, Supabase for auth/DB/storage, FastAPI for server-side-only logic) and scope (assignments/quizzes/grading and live video are explicitly excluded from this MVP — async content delivery only). This plan lays out the data model, auth model, frontend architecture, FastAPI responsibilities, repo layout, phased build order, deployment, and verification approach so implementation can proceed phase-by-phase with each phase independently demoable.

## Execution Order (per latest direction)

Build **frontend-first**: implement the React+Vite UI (landing/marketing pages plus staff/student app shells) before wiring Supabase/FastAPI backends. Landing pages in particular must be strong on SEO (semantic HTML, meta/OpenGraph tags, proper heading hierarchy, fast Lighthouse scores, sitemap-friendly routing) and polished with Framer Motion animations. Use the `awwwards` skill (mandated for all frontend/UI work) plus other relevant design skills (`ui-ux-pro-max`, `frontend-design`, `dataviz` if charts appear on dashboards) while building.

## Stack Summary

- **Frontend**: React + Vite, TypeScript, Tailwind CSS, Framer Motion, React Router v6, TanStack React Query, `@supabase/supabase-js`
- **Data/Auth/Storage**: Supabase (Postgres + Row Level Security, Supabase Auth, Supabase Storage, Realtime)
- **Backend service**: FastAPI (Python) — only for secret-holding/server-only work: invitation & notification emails, reporting/aggregation, scheduled jobs
- **Deployment**: Vercel (frontend), Render (FastAPI), Supabase hosted project

## 1. Data Model (Supabase Postgres)

All tables in `public` schema, `uuid` PKs (`gen_random_uuid()`), `timestamptz` timestamps, RLS enabled on every table.

**Identity**
- `profiles` (id → auth.users, `role` enum `staff|student`, full_name, email, avatar_url, phone, bio, is_active) — auto-created via trigger on `auth.users` insert, role read from signup metadata.

**Courses & Content**
- `courses` (title, slug, description, cover_image_url, status `draft|published|archived`, created_by)
- `course_instructors` (course_id, instructor_id) — many-to-many staff↔course
- `modules` (course_id, title, description, position)
- `lessons` (module_id, title, content_type `video|document|slides|link|text`, body_text, external_url, position, is_published)
- `lesson_materials` (lesson_id, file_name, storage_bucket, storage_path, mime_type, size_bytes, uploaded_by)
- `lesson_progress` (student_id, lesson_id, completed, completed_at, last_viewed_at)
- Storage buckets: `course-materials` (private, signed URLs), `course-covers` (public-read), `avatars` (public-read)

**Enrollment & Rosters**
- `sections` (course_id, name, start_date, end_date, capacity) — a specific offering/cohort of a course
- `enrollments` (student_id, section_id, status `invited|active|completed|dropped`, enrolled_at)
- `invitations` (email, role, section_id, invited_by, token, status `pending|accepted|expired|revoked`, expires_at)

**Attendance & Scheduling**
- `calendar_events` (section_id, title, event_type `class_session|office_hours|exam_free_event|other`, location, starts_at, ends_at, created_by)
- `attendance_records` (event_id, student_id, status `present|absent|late|excused`, marked_by, marked_at, note)

**Announcements, Discussions, Messaging**
- `announcements` (section_id, course_id, title, body, created_by, pinned)
- `forum_threads` (section_id, title, created_by, is_locked, is_pinned)
- `forum_posts` (thread_id, author_id, body, deleted_at soft-delete)
- `conversations`, `conversation_participants` (conversation_id, profile_id, last_read_at), `messages` (conversation_id, sender_id, body) — Supabase Realtime powers live updates on `messages` and `forum_posts`

**RLS approach**: reusable SQL helper functions `is_staff()`, `is_enrolled(section_id)`, `teaches_section(section_id)`. Staff generally get full CRUD (optionally scoped to `course_instructors`); students get read scoped to their own enrollments/rows and write only on their own data (progress, own posts, own profile fields excluding `role`). Storage bucket policies mirror the same helper functions.

**Deferred schema additions** (from a later product gap review — not yet scheduled, no Supabase project exists yet to apply any of this against; recorded here so it isn't lost before Phase 1):
- `lessons.prerequisite_lesson_id` (or a position-based lock rule) — enables **sequential lesson unlocking**, enforced in RLS + client nav, so a student can't jump ahead of an incomplete lesson.
- `certificates` (`id, student_id, course_id, issued_at, certificate_code, pdf_url`) — **course completion certificates**, generated by FastAPI once `lesson_progress` hits 100% for a course. (`certificate_code`: a short human-verifiable code, e.g. for a "verify this certificate" lookup page — refinement suggested by an external plan-review pass, worth keeping.)
- A real editor spec (e.g. TipTap) for `lessons.body_text` / `announcements.body`, which are plain strings today — instructors currently can't format lesson/announcement content (code blocks, tables, etc.).
- `notifications` (`id, user_id, title, body, type, read_at, link_url`), Realtime-driven — an **in-app notification center**, surfaced as a bell/tray in `AppShell`'s topbar next to the current nav-only `GlobalSearch`. `type` should be a real enum (`announcement | event | system | direct_message`) rather than a free string, so the bell tray can route/icon each notification correctly.
- `profiles.is_admin` (or an expanded role enum) — distinguishes a global **admin** from an **instructor** scoped to their own `course_instructors` rows; `profiles.role` is only `staff|student` today.
- `courses.category` / `courses.tags` — course categorization, surfaced as filters on `StaffCoursesPage`/`StudentCoursesPage`.
- Postgres full-text search (`tsvector`) via a Supabase RPC over lessons/forum posts/announcements — a real superset of `AppShell`'s current nav-only `GlobalSearch`.
- A FastAPI reporting endpoint (`/api/v1/reports/at-risk-students`) surfacing inactivity/behind-cohort signals — a natural future addition to the Staff Dashboard's "Courses needing attention" card.

## 2. Auth & Roles

- Supabase Auth (email+password / magic link). No self-serve *role picker* — but `/signup` is public and always creates a **staff** account (this is a teaching tool; anyone signing up directly is staff). Students never self-register: they only get an account via a staff-sent invite, landing on `/accept-invite` to set a password and get auto-enrolled in the section named by the invite token.
- React `AuthProvider` context loads session + `profiles` row, exposes `{ user, profile, role, loading }`. `<ProtectedRoute role="staff|student|any">` gates routes, redirecting unauthenticated users to `/login` and role-mismatches to a `/not-authorized` page.
- `/login`, `/signup`, `/accept-invite`, and `/reset-password` pages handle every auth flow via Supabase Auth. Full page-by-page design for each is in **§9**.

## 3. Frontend Architecture

**Folder structure** (`frontend/src/`): `routes/` (router + ProtectedRoute), `layouts/` (StaffLayout, StudentLayout, AuthLayout), `features/{auth,courses,enrollment,attendance,scheduling,announcements,discussions,messaging,dashboard}/` each with `pages/`, `components/`, `hooks/`, plus shared `components/ui/` (Tailwind + Framer Motion primitives: Button, Modal, Table, Tabs, Toast), `lib/` (`supabaseClient.ts`, `apiClient.ts` for FastAPI calls, `queryClient.ts`), `types/database.types.ts` (generated via `supabase gen types typescript`).

**Routing**: `/staff/*` and `/student/*` route trees under their respective layouts — dashboard, courses (catalog/editor/roster), invitations, attendance, calendar, announcements, forums, messages. Public routes: `/login`, `/accept-invite`, `/reset-password`.

**Data fetching**: `@supabase/supabase-js` for all direct CRUD/auth/storage/Realtime; TanStack React Query wraps every Supabase call for caching/loading/error state, keyed consistently per feature (e.g. `['courses', courseId]`). Realtime channels feed new rows directly into the Query cache for messages/forum posts.

**Styling/motion**: Tailwind theme extended with brand tokens; Framer Motion centralized in `components/ui/` primitives (page transitions, list stagger, modal enter/exit) rather than redefined ad hoc per feature.

**Key screens**:
- *Staff*: dashboard, course/module/lesson editor with material upload, roster manager, invitation sender, attendance marking grid, calendar management, announcement composer, forum moderation, messaging inbox.
- *Student*: dashboard, course catalog + enrollment, lesson viewer with mark-complete, personal calendar, attendance history, announcements feed, forum participation, messaging.

## 4. FastAPI Service

Scope limited to what can't safely run client-side: invitation/notification emails, reporting/aggregation, scheduled jobs — using the Supabase **service-role key** (bypasses RLS, so every endpoint must independently verify the caller's JWT and role via a `require_staff` dependency).

Structure (`backend/app/`): `core/` (config, JWT verification, service-role Supabase client), `api/v1/` (`invitations.py`, `reports.py`, `notifications.py`), `services/` (`email_service.py`, `reporting_service.py`), `jobs/` (APScheduler-based nightly jobs: expire stale invitations, close out completed enrollments, digest emails). Frontend calls these via `lib/apiClient.ts`, attaching the Supabase access token as a Bearer header.

## 7. Deployment

- **Supabase**: hosted project, schema applied only via `supabase db push` from `supabase/migrations/` (never hand-edited in the dashboard), auth redirect URLs configured for Vercel domain(s).
- **Frontend (Vercel)**: root `frontend/`, build `npm run build`, output `dist/`, env vars per environment.
- **Backend (Render)**: web service from `backend/` (Dockerfile), all secrets server-side, optional Render Cron Job for scheduled tasks.
- **Staging environment**: before Phase 7, stand up a staging Supabase project + staging Vercel/Render deploys mirroring production configuration (same RLS policies, same env var shape, seeded with representative data). Realtime features (messaging, forum live updates) and scheduled jobs are debugged here, never against the live production database.
- **CI/CD pipeline gates** (`.github/workflows/frontend-ci.yml`, `backend-ci.yml`): every PR runs typecheck/lint/build, the Playwright E2E suite, and the pytest suite; a Lighthouse CI budget check runs on the frontend workflow. Merges to `main` are blocked if any suite fails or the Lighthouse performance/accessibility score regresses below the agreed threshold.

## 8. Verification

- **RLS**: local Supabase CLI stack, test staff-vs-student access boundaries per table (cross-section reads, write restrictions, role-escalation prevention) before and after each phase touching RLS. Explicitly attempt role-escalation (student writing their own `role`, student writing another student's rows) and confirm denial.
- **End-to-end automation (Playwright)**: automate the critical journeys — full enrollment loop (invite → accept → enroll → appear on roster), lesson view → mark-complete, and real-time messaging (two-session send/receive) — so regressions are caught on every PR, not just manually before a release.
- **Negative & edge-case testing**: beyond RLS boundaries, inject malformed/oversized payloads into FastAPI endpoints and assert clean 4xx responses (not 5xx or silent acceptance); test invitation tokens that are expired, revoked, or reused; test a student dropping a course mid-lesson and confirm progress/attendance state stays consistent.
- **Manual staff flow**: create course → modules/lessons → upload material → create section → invite student → mark attendance → post announcement → moderate forum → message student.
- **Manual student flow**: accept invite → browse/enroll → view lesson/mark complete → view calendar/attendance → read announcement → post in forum → message staff.
- **FastAPI**: `pytest` + `httpx.AsyncClient`, test `require_staff` rejects non-staff JWTs, test invitation/report endpoints against seeded data, plus negative tests for the scheduled jobs (a failed email send or malformed row must not abort or corrupt the rest of the job run).
- **Realtime**: two-session test (staff + student) confirming live message/thread updates without refresh, run first against staging before being trusted in production.
- **Continuous UI/UX & accessibility audits**: at the end of each frontend-heavy phase (2, 3, 5, and again before Phase 7), run a Lighthouse pass (performance, accessibility, SEO) and a manual audit of semantic HTML structure and Framer Motion animation performance (60fps target, `prefers-reduced-motion` respected) — not deferred to a single end-of-project pass.
- **Pre-deploy checklist**: RLS suite against hosted (not just local) project, env vars verified in Vercel/Render, CORS restricted to production origin, Storage buckets denying anonymous access, full CI suite (Playwright + pytest + Lighthouse budget) green on staging before promoting to production.

### 9.1 Auth Pages

**`/login`**
- Fields: Email, Password, "Remember me", "Forgot password?" → `/reset-password`.
- Errors: single generic banner "Invalid email or password" (never reveal which field failed).
- Copy: H1 "Welcome back"; subtext "Sign in to your HanbeeLms account."; footer "New here? Staff can create an account →" links to `/signup` (no student-signup mention).
- Submit (conceptually): `supabase.auth.signInWithPassword`, then AuthProvider loads `profiles.role`, redirect to `/staff/dashboard` or `/student/dashboard`.
- Decorative panel: neutral dimmed dashboard preview, no role toggle (role resolves server-side).

**`/signup`** (staff self-signup only)
- Fields: Full name, Email, Password, Confirm password, Terms checkbox. No role selector — role is hardcoded `staff` in signup metadata.
- Validation: optional strength meter (amber=weak/teal=strong), min 8 chars, confirm-match inline error, "email already registered" surfaced as inline banner.
- Copy: H1 "Create your staff account"; subtext "HanbeeLms is built for instructors and admins — set up courses, invite students, and run your sections."; disambiguation note under the form: "Are you a student? You'll receive an invite link from your instructor — no signup needed here."
- Submit (conceptually): `supabase.auth.signUp({..., options:{data:{role:'staff', full_name}}})` → trigger creates `profiles` row → redirect `/staff/dashboard`.
- Decorative panel: reuse `HeroVisual`'s `CoursesScreen`/`EnrollmentScreen` mockups; caption "Set up your first course in minutes."

**`/accept-invite?token=...`**
- States: *loading* (skeleton while token validates) → *valid* (read-only "Joining: {Course} — {Section}" violet-soft chip, editable Full name pre-filled if provided, Password/Confirm; email read-only from invitation) → *invalid/expired/revoked* (form replaced by error state: `EnrollmentIcon` in amber, "This invite link is no longer valid", CTA "Contact your instructor") → *already-accepted* (redirect to `/login` with banner "This invite was already used — sign in instead").
- Copy: H1 "You're invited" (use `EnrollmentIcon`, not emoji, to match the hand-drawn icon aesthetic); subtext "Set a password to join {Section name}."
- Submit (conceptually): set password bound to the invited email + mark `invitations.status='accepted'` + insert `enrollments(status='active')` (one atomic step, likely an RPC) → redirect `/student/dashboard`.
- Decorative panel: `EnrollmentScreen`-style mockup showing the actual section name being joined.

**`/reset-password`** (two-step, same route, state-driven)
- Step 1 (request): Email field, "Send reset link"; success replaces the form with a confirmation panel (checkmark, "Check your inbox") rather than a toast.
- Step 2 (via emailed recovery link): New password + Confirm, submit updates password, redirect `/login` with success banner.
- Submit (conceptually): `supabase.auth.resetPasswordForEmail` then `supabase.auth.updateUser({password})`.

### 10.14 Accessibility: Color-Contrast Audit — Real WCAG AA Failures Found and Fixed

This was not a clean spot-check — computing actual WCAG contrast ratios for the OKLCH palette in `index.css` (relative luminance formula, via a scratch Node script since no color library is installed) turned up several genuine AA failures, some severe:

| Pairing | Ratio | AA-normal (4.5:1) |
|---|---|---|
| `--color-mist` text on `--color-paper`/`--color-cloud` | 2.6–2.8:1 | **FAIL** |
| `--color-teal`/`--color-amber` as literal text (soft-badge or direct) | 1.7–2.3:1 | **FAIL** |
| `--color-paper` text on solid `--color-teal`/`--color-amber` backgrounds | 1.8–2.3:1 | **FAIL** |
| `--color-paper` text on solid `--color-error` | 4.2:1 | fails (large-text-only) |
| `--color-error` as literal text on `--color-error-soft` | 3.6:1 | fails (large-text-only) |

`--color-mist` was the most severe and widespread — it's used for virtually every timestamp/meta-text/table-header string across the entire app, and was reading at under 3:1, below even the large-text AA threshold.

**Fixes, verified against exact target ratios before touching any file:**
- Darkened `--color-mist` (`oklch(0.68 → 0.54 0.012 265)`) — one token change, fixes every meta-text instance app-wide, no call sites touched. Now 4.9–4.6:1.
- Darkened `--color-error` (`oklch(0.6 → 0.54 0.19 25)`) — a single sweet-spot value that fixes *both* its use cases at once (paper text on solid error backgrounds: 4.2→5.4:1; error text on error-soft backgrounds: 3.6→4.5:1), so no call sites needed changing there either.
- Added `--color-teal-deep` (`oklch(0.5 0.13 175)`) and `--color-amber-deep` (`oklch(0.52 0.15 85)`), mirroring the `--color-violet-deep` pattern that already existed. Teal and amber's *base* tokens stay as-is (they're fine for icons/decorative chips, which aren't subject to text-contrast rules) — only literal text that was using them directly got swapped to the `-deep` variant: every status-badge `Record<Status, string>` map (`StaffRosterPage`, `StaffInvitationsPage`, `StaffCoursesPage`, `StudentAttendancePage`), the Discussion Forums "Pinned" badge and its moderator Pin button, the Course Editor's "Draft" lesson badge, both dashboards' badges, `StudentCoursesPage`'s "Enrolled" badge, `StudentEnrollmentsPage`'s "Completed" badge, `CalendarAgenda`'s "Office hours" chip, and two literal-text spots on the public landing page (`AudienceSplit`'s "For Staff" kicker, `Hero`'s animated headline word, and `HeroVisual`'s mockup stat labels — decorative illustration, but it does contain real readable text, so it wasn't exempted).
- Solid teal/amber backgrounds paired with white text (`StaffAttendancePage`'s Present/Late toggle buttons, `StudentLessonViewerPage`'s "✓ Completed" button) switched to `text-(--color-ink)` instead — dark text on a light-hued solid background, rather than darkening the base color itself (which would have changed the brand color everywhere it's used, including places where contrast isn't an issue).

**Explicitly not touched**: icon-only chips (`<span className="... bg-X text-Y"><SomeIcon /></span>`) — icon glyphs aren't subject to WCAG 1.4.3 text contrast, and their thicker strokes already read fine at the existing lightness; changing those would alter the app's visual identity for no accessibility benefit.

Verified: full `npm run test:e2e` suite (25 specs) still passes unchanged — no test asserted on the old colors — plus a manual Playwright visual check of the Roster and Attendance pages confirming the new badge/button text reads as richer, more legible color rather than washed-out or visually broken.

### 10.31 Completing the §10.30 Deferrals: Real WCAG Contrast Audit + a Genuine Token-Architecture Bug

Closed both items §10.30 explicitly flagged as not covered — the sub-pixel overflow discrepancy and a real computed-contrast pass on the pages dark mode hadn't been screenshot-verified against.

**The 4px landing-page overflow did not reproduce.** Direct measurement (`document.documentElement.scrollWidth` vs `clientWidth` at 390px) came back exactly equal (375/375). Likely a one-off timing artifact from the prior pass, not a live bug — no fix needed, confirmed rather than assumed.

**The real contrast audit found a genuine, non-obvious bug class** — not the kind a screenshot eyeball catches, since every instance *looks* like a normal button/pill at a glance:

`--color-ink` and `--color-paper` are the app's adaptive text/background pair — they deliberately *swap roles* in dark mode (that's what makes ordinary text repaint correctly everywhere for free, per §10.28). But a handful of elements use these two tokens for a different purpose: **a permanently dark accent** — a marketing card, a CTA banner, a colored status pill — that's supposed to look the same regardless of site theme, or supposed to pair with a bright accent color (teal/amber) that *doesn't* swap roles. Once dark mode inverts `--color-ink` to near-white, every one of these breaks: a "for staff" marketing card silently becomes a light card with unreadable text, and a teal "Present" attendance pill gets near-white text on a bright teal fill (measured contrast ratio 1.64:1 — nowhere close to the 4.5:1 AA minimum).

Found via a real computed-contrast script (canvas-normalized `getComputedStyle` colors — necessary because this browser returns `oklch()` strings, not `rgb()`, so a naive regex-based first attempt silently matched nothing and falsely reported zero failures; redone properly before trusting the result), run against all 10 public routes plus a representative slice of each authenticated role, in dark mode, at 1280px.

**Fix — two new theme-invariant tokens**, `--color-ink-fixed`/`--color-paper-fixed` (`index.css`), holding the light-mode `ink`/`paper` values permanently, deliberately absent from both dark-mode override blocks. Applied everywhere the "always dark, not theme-following" pattern was found:
- `components/landing/AudienceSplit.tsx` — the "For Staff" card (bg, text, list-item text, and its CTA button)
- `components/landing/CTA.tsx` — the full-page dark banner section (bg, text, and both outline buttons)
- `components/landing/HeroVisual.tsx` — the "48 students online" floating badge (its sibling badge already used adaptive `--color-paper`/light-card styling correctly, so only this one dark-styled badge needed the fix)
- `pages/staff/StaffAttendancePage.tsx` — the Present/Late status pill text (Absent/Excused were already correct, since they pair a bright/light chip with `--color-paper` text, which correctly becomes dark text in dark mode)

### 10.38 A Real, Live Vulnerability Found and Closed: Separate Signup Paths for Staff / Student / Manager

The user asked how each of the three roles should sign up for the first time — answering that honestly required first checking whether the existing signup design was even safe, and it wasn't.

**The hole.** `handle_new_user()` (0001_init.sql) cast `raw_user_meta_data->>'role'` straight from the client's `auth.signUp()` call into the new profile, with no server-side check. Since that call runs in browser JS against only the public anon key, anyone could open devtools and call `supabase.auth.signUp({ email, password, options: { data: { role: "manager" } } })` and grant themselves permanent org-wide access — bypassing every RLS policy gated on `is_staff_or_manager()`. This wasn't a hypothetical: it's the exact mechanism `SignupPage.tsx` already used for legitimate staff self-signup (`role: "staff"`), just with no floor stopping `"manager"` too. Attempting to demonstrate it live hit Supabase's email rate limit (the same constraint from §10.37) before a session could be created, but reading the trigger's code alone was enough to confirm the hole — an exploit doesn't need to succeed live to be real.

**The design, and the fix.** Presented the user two standard ways to bootstrap a first admin (first-user claim vs. always-invite-only); they chose first-user bootstrap, then asked the natural follow-up — what happens for the *second* manager? Answer: every manager after the first is invited by an existing one, the same mechanism already built for students. This became one coherent rule, moved server-side into `handle_new_user()` (`migrations/0004_role_signup_security.sql`), decided in order: **(1)** a matching, not-yet-accepted `invitations` row for this exact email wins outright regardless of what the client requested (and is marked accepted — a student invite tied to a section also creates the real `enrollments` row immediately, closing that loop too); **(2)** requesting `'manager'` only succeeds if this is the very first manager in the whole system, otherwise it silently becomes `'student'` rather than erroring, so a probe can't even confirm the check exists; **(3)** requesting `'staff'` is honored as-is — deliberate, unchanged self-service design; **(4)** anything else defaults to `'student'`. New `manager_exists()` and `get_invitation()` RPCs, both `security definer` and narrowly scoped (a boolean; an invitation's public-safe display fields only), granted to `anon` so unauthenticated pages can use them safely.

**Verified the exploit and the fix, not just the code.** Reused the `@electric-sql/pglite` real-Postgres harness (§10.35/§10.36) to run six scenarios against the actual migration file: a plain signup defaults to student; requesting staff is honored; the *first* manager claim succeeds (proving the bootstrap works); a *second* manager claim on the same fresh database is silently downgraded to student (proving the exact exploit that worked against the original trigger is now blocked); `manager_exists()` reports correctly; and a pending invitation overrides a client's manager request entirely, marks itself accepted, and creates a real enrollment. ### 11.11 A real vulnerability in the tournament registration flow, caught by the user, fixed the same day

The user spotted it directly from a screenshot: the "I've completed the payment via QR scan" checkbox on `TournamentPage.tsx`'s registration form was purely client-side state, sent straight through to `payment_confirmed` on insert. The QR-code-tampering scenario they described (editing the displayed image via devtools) was the visible symptom, but the real bug was worse — since `tournament_registrations`' INSERT policy was `with check (true)` (anyone, including anonymous, can insert), nothing stopped a request from skipping the UI entirely and calling the Supabase REST API directly with `{ "payment_confirmed": true }`, no payment at all, no checkbox interaction required.

Fixed with `0010_tournament_registrations_trust_fix.sql`: a `before insert` trigger that unconditionally forces `payment_confirmed = false` and `status = 'pending_verification'` on every new row, ignoring whatever the client sends for those two columns — the database, not the client, now owns that trust boundary. A new UPDATE policy restricts changing either field to `is_staff_or_manager()`, so the only real path to a "verified" registration is a staff member manually checking their UPI transaction history against the driver's name/email and updating the row themselves — the same manual-verification shape already established elsewhere in this app (`ManagerVerificationsPage`, the staff-approval gate).

Validated against pglite before applying live, 8 scenarios: a direct client-supplied `payment_confirmed=true`/`status='verified'` insert lands as `false`/`pending_verification` regardless; a normal registration lands the same way; anonymous can't read registrations back; anonymous can't update `payment_confirmed` on any row, including their own; staff/manager can both read all registrations and successfully mark one verified. One real, useful thing learned while writing the test itself, not assumed: `INSERT ... RETURNING` requires the inserting role to also satisfy a SELECT RLS policy — confirmed via a minimal repro that this is real Postgres behavior, not a pglite quirk. Checked the actual frontend code (`tournamentApi.ts`) before treating this as a concern: it does a plain `.insert()` with no `.select()`/RETURNING, so this doesn't affect the real app — only the test script needed adjusting to match. `ScanToPayCard.tsx`'s copy updated to be explicit that the checkbox is a self-declaration pending manual staff confirmation, not proof of payment. Applied live via the pooler connection, confirmed the trigger and all three policies exist as expected; `tsc --noEmit` clean.

### 2026-09-24 — RLS security audit: four real vulnerabilities found, proven live, and fixed (migrations 0016, 0017)

Prompted by two shipped RLS bugs found incidentally earlier (client-settable `payment_confirmed`, the `conversation_participants` recursion), a deliberate policy-by-policy pass was started. The first audit agent was stopped mid-run at the user's request after it had already applied 0016 live; this entry records what was independently re-verified afterward. **Audit coverage caveat**: the interrupted run's claim that every table in 0001-0015 was reviewed was not independently confirmed; the four findings below are each proven live, but absence of further findings is not proof of absence.

**Confirmed vulnerabilities (each exploited live via impersonated pooler queries, rolled back, then re-verified blocked after the fix):**
1. **`profiles` self-promotion** — the self-update policy's implicit WITH CHECK only constrained `id`, so a student could `update profiles set role='manager', approved=true` on their own row: instant approved manager, defeating every `is_staff_or_manager()` check and the 0005 staff-approval gate. Fixed in 0016 with a BEFORE UPDATE trigger (`guard_profile_self_escalation`) that pins `role`/`approved` unless the caller is a manager. Role assignment happens only at signup (INSERT), so the manager bootstrap is unaffected.
2. **`auto_attendance_sessions` forgery** — a client could directly `update ... set status='present', ended_at=now()`, bypassing `heartbeat()`/`finalize_my_session()`. Fixed in 0016: a trigger reverts guarded columns unless a transaction-local flag is set, and both RPCs became SECURITY DEFINER and set it.
3. **`certificates` forgery** — a client could insert a certificate with any `course_title`/`serial`. Fixed in 0016: direct INSERT policy dropped, `issue_certificate()` made SECURITY DEFINER. **Still open (business logic, not RLS)**: `issue_certificate()` does not check that the course was actually completed.
4. **`staff_time_entries` forgery** (found during this re-verification, not by the first agent) — staff could insert backdated rows (a 400-day-old entry was accepted with `on_time=true`) or rewrite their own `clock_in`/`on_time`, undermining manager oversight. Fixed in 0017: trigger forces `clock_in := now()`, `on_time := true`, rejects `work_date` more than a day from the DB date, and only permits a first `clock_out` (set to `now()`). Calls with no `auth.uid()` (SQL editor/admin) bypass the guard so real corrections stay possible. `on_time` is always `true` today because no late cutoff exists yet; a real cutoff must be computed server-side here.

**Verified live after the fixes (14 checks, all rolled back, zero leftover rows):** each exploit above is neutralized; a student can still update their own `full_name`; a manager can still change another profile's `approved`; `heartbeat()`, `finalize_my_session()`, and `issue_certificate()` (including idempotency) still work; clock-in/clock-out still work.

**Known remaining observations, not changed (product decisions, flagged for the owner):** any signed-in user can read every `profiles` row (including emails); published lesson content is readable by all signed-in users regardless of enrollment; `course_applications` accepts unauthenticated inserts with no rate limit (spam risk).

## 2026-09-24 — Backend audit: certificates, discussions, invitations (migration 0018)

All exploits proven live on the pooler as impersonated users in rolled-back transactions, then re-run after applying 0018.

Findings:
1. CONFIRMED: issue_certificate minted a certificate for any title (ava got one for "No Such Course", and for her course while 2 of 3 lessons were done). Fix: RPC now requires a published course, an enrollment, >=1 published lesson, and a lesson_completions row for every published lesson; idempotency and serial format kept; SECURITY DEFINER, search_path=public.
2. CONFIRMED: a student could create a thread with pinned/locked=true and update them on their own thread. Fix: trigger guard_discussion_thread (non-staff pinned/locked forced false on insert, unchangeable on update).
3. CONFIRMED: students could post into locked threads. Fix: trigger guard_discussion_post rejects non-staff inserts into locked threads.
4. RULED OUT: author_id reassignment was already blocked by RLS (implicit WITH CHECK). Triggers additionally make author_id/course_id/thread_id immutable.
5. CONFIRMED: invitations.invited_by could be forged (jamie inserted with morgan's id). Fix: trigger guard_invitation forces auth.uid().
6. CONFIRMED escalation: staff could invite role='manager'/'staff'; handle_new_user copies the invite role at signup, pre-approved (bypasses staff approval). Fix: only managers may create/update non-student invites.
Unauthenticated (admin SQL) calls bypass all guards.

New lib modules (data-access only, NOT wired into any page): certificatesApi.ts (fetchMyCertificates, issueCertificate, verifyCertificate(certificateId) wrapping existing verify_certificate(uuid) RPC, fetchAllCertificatesForStaff), discussionsApi.ts (fetchThreads, createThread, fetchPosts, createPost, setThreadPinned, setThreadLocked, deletePost, deleteThread), invitationsApi.ts (fetchInvitations, createInvitation, deleteInvitation).
